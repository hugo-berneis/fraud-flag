Pros & Cons by Approach

Rules Engine

RulesEngine.java
Pros
  • Zero latency: 0.07ms average in this run, no network call at all
  • Fully deterministic and explainable -- the exact condition is visible in the diff
  • No API cost, no dependency on an external service being up
  • Catches the fraud patterns the generator itself injects, by construction
Cons
  • Only as good as the rules someone wrote -- a new pattern needs a new rule
  • Binary: no notion of "a little suspicious" vs. "extremely suspicious"
  • Easy to write a rule that's too broad and silently swallows edge cases
Best fit

The small number of fraud patterns with an unambiguous signature -- a burst of tiny card-testing charges, an amount 10x the account's usual spend. Exactly Phase 3's "obvious cases" design intent.

Jev

DecisionClient / MockDecisionClient
Pros
  • Structurally bounded: noul() always returns boolean+confidence, choice() always returns one of the given fraud types -- can't answer outside that shape
  • Fast enough to run on every transaction that reaches it (136/240 here, <0.1ms avg)
  • The interface seam means a real Jev client swaps in later with zero other code changes
Cons
  • Still MockDecisionClient here -- no real Jev/TypeSafe calibration data exists for this project yet, unlike confidence-audit's project where a real smoke test already ran
  • Mock confidence is a simple suspicious-category count, not a trained/calibrated score
Best fit

The ambiguous middle: cases a rule doesn't confidently resolve but still need a fast, bounded fraud/not-fraud call to decide routing.

LLM (Claude Haiku 4.5)

CaseSummaryClient / AnthropicCaseSummaryClient
Pros
  • The only one of the three that writes prose a human reviewer can actually read
  • Real and wired, not mocked -- actually called Claude Haiku 4.5 in the run behind this doc
  • Never asked to decide, only to explain -- its failure mode can't silently flip a route
Cons
  • By far the slowest path measured: 8.5s average, 23s max in this run, vs. sub-millisecond for the other two -- only viable gated to ~1% of traffic
  • Costs money per call, unlike the other two
  • One of three live calls in this run returned an empty response with no error -- needs a retry/fallback that doesn't exist yet
Best fit

Exactly the ~1% of cases that reach REVIEW -- never routing itself, only making the human reviewer's job faster once a transaction is already flagged as ambiguous.

Why Rules First, Jev Fallback, LLM Last?

The pipeline is layered cheapest-and-fastest-first. A hard rule runs first and, when it fires, decides the route for free in well under a millisecond -- no network call, no cost, fully explainable. Anything a rule doesn't confidently resolve falls to Jev, still bounded and still fast, trading a little certainty for coverage of the ambiguous middle. Only the rarest already-escalated case -- about 1% of traffic in this run -- ever pays the latency and dollar cost of a real LLM call, and even then the LLM never decides: it only writes a case summary for the human who does. This is CLAUDE.md's explicit design, not something improvised after the fact: "the LLM is called only for uncertain cases... and never makes the decision."
